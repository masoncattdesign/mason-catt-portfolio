Overview

A payment design system built for speed

Amazon Business does not have one payment flow. It has a matrix of them: card, bank account, wallet, buy-now-pay-later, benefits cards, market-local schemes, each multiplied by the market it launches in and the account type paying. Before the Pay Studio, every cell in that matrix was drawn by hand. The same sheet, the same wallet row, the same verification step, redrawn a little differently every time.

The Pay Studio reorganizes that work into an atomic structure: components that compose into templates, templates that connect into use cases. Each layer is closed over the one below it, so a designer building a new payment experience picks from the layer above rather than starting at a blank frame.

The argument
The expensive part was never the drawing. It was the drift: six versions of the same sheet, four pixels apart, each behaving slightly differently.

Where it started
01

Every method was a project

Adding a payment method looks like a small job and is not. A new method needs a place in the wallet, an entry in the add-new list, a form built to its own rules, some kind of verification, a confirmation, and a return to the wallet with the new method selected. None of that is novel design work. All of it got designed again each time, because there was nothing to inherit. The result was a set of screens that were each individually fine and collectively inconsistent, which is the specific failure a design system exists to prevent.

The surface
A bottom sheet over checkout. Small, dense, and the last thing between a business customer and a completed order, so every inconsistency is expensive.
The variables
Method type, market, account type, eligibility, and whether the method hands off to a third party. The combinations grow faster than a team can draw them.
The failure mode
Not ugliness. Drift. Near-identical sheets with different spacing, different label logic, and different behavior on the same control.
The model
02

Three layers, component to journey

The system borrows atomic design's logic and stops at three layers, because three is what the problem actually needs. Components are the parts. Templates are complete task interfaces assembled from those parts. Use cases are templates wired together into a journey a customer finishes. Each layer only reaches one level down, which is what keeps the whole thing from collapsing back into a pile of screens.

Layer one

Components

The parts a payment interface is actually made of. A wallet row, a field with its brand badge, a balance toggle, a primary action, a security note. Each one owns its own states and its own label logic, so a template never has to decide how a selected card should look.

Layer two

Templates

Complete, standalone interfaces for one task: choose a method, pick a bank, enter card details, verify a number, confirm success. Every template is a specialization of one base sheet, which is why they stay consistent without anyone policing them.

Layer three

Use cases

Templates wired into a journey that a customer finishes. The use case is where the product decision lives: which templates, in what order, with what branches. Nothing new is drawn at this layer, which is the whole point.

Layer one
03

Eighteen components

Components are the building blocks of the Pay Studio. I built 18 unique components, and the useful thing about them is not the count, it is that they share an anatomy. Almost every row in a payment interface is the same shape: an asset, a primary label, a secondary label, a trailing control, and a selection state. Once that shape is a component, a Venmo account and an EBT card and a promotional balance are all the same row with different content, and they cannot drift apart.

  1. 1Asset slot. Card art, network mark, or partner logo, always the same footprint.
  2. 2Primary label. Method name and masked identifier, formatted by the component.
  3. 3Secondary label. Owner, expiry, balance, or an eligibility note.
  4. 4Trailing control. Toggle, chevron, or nothing, depending on what the row does.
  5. 5Selection state. One treatment, applied identically across every method type.
The shared anatomy. Every method row in the system is this shape with different content.

Layer two
04

One base sheet, eight tasks

Templates are standalone interfaces for performing a specific task, grouped by the kind of work they do. The decision that made them hold together was refusing to design them as eight separate sheets. There is one base template with a fixed skeleton, and every task template is that base with its body slot filled. Consistency stops being something a reviewer enforces and becomes something the file cannot violate.

  1. 1Sheet chrome. Back, brand mark, dismiss. Fixed, so navigation never varies by task.
  2. 2Title block. Heading plus optional subcopy, the only place a task explains itself.
  3. 3Body slot. The variable region, filled with components. This is the only part a task template changes.
  4. 4Primary action. One per sheet, in one position, always.
  5. 5Security note. The encryption line, present wherever credentials are entered.
The base template. Every task sheet in the system is this skeleton with a different body slot.
The template library, grouped by task. The plain Heading / Message / Button sheet in the middle is the base every other template inherits from.

Layer three
05

A payment method, end to end

A use case connects templates into a journey a customer completes. The test of the system is whether an awkward method fits it without special pleading, so the one worth walking through is a market-local scheme rather than a credit card. BANCOMAT Pay registers against a phone number instead of a card number and hands off to the customer's bank app to authorize, which is exactly the kind of method that used to justify a bespoke flow. Here it is four templates in sequence, and the only new work is the content of one body slot.

The BANCOMAT Pay pathway. A method that authorizes through the customer's bank app, assembled entirely from existing templates.

The measure of the system is what it does not require. Adding this method meant one new list row, one body slot, and one line of copy about redirection. No new sheet, no new selection treatment, no new success state.

After

What it changed

The Pay Studio moved payment work from drawing to assembly. A new method became a question of which templates and in what order, which is a product conversation rather than a design backlog item, and the sheets stopped drifting apart because nobody was redrawing them.

The same structure, components underneath templates underneath journeys, is what I carried into the Amazon Business Credit Card ECM experience the following year, and it is the shape of the work I do now on Windows Design Systems.
